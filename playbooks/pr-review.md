# Playbook: проверка Pull Request

1. Получить фактические base/head SHA, дифф и описание PR.
2. Оценить требования, затронутые зависимости, нежелательные изменения и риск регрессий.
3. Проверить существующие тесты и наличие новых.
4. Проверить реальные CI workflow/checks именно для текущего HEAD.
5. Отдельно изучить визуальные артефакты и пользовательские сценарии, если интерфейс затронут.
6. Сформулировать findings с severity, точным местом и конкретным действием.
7. По политике main-first после успешных обязательных checks/reviews завершить merge PR в `main`; если правила позволяют работу в `main` напрямую, не создавать PR без нужды.
8. Подтвердить результат в `origin/main` на точном SHA, затем безопасно удалить только собственную временную ветку. При squash проверять merged PR и итоговый diff, а не только ancestry.
9. Если merge блокируется — оставить PR/ветку и сообщить `BLOCKED`.

**Нельзя:** доверять старому PASS, обходить protection, удалять чужую/незамерженную ветку. См. [branch-finalization](branch-finalization.md).

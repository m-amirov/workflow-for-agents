# Общие правила проектирования интерфейсов

**Область:** новые и изменяемые web/product UI, адаптивные экраны и дизайн-системы. Не применять к backend, текстовым правкам и игровым ассетам без UI-задачи.

1. Сначала выяснить целевое действие пользователя, реальные ограничения проекта, утверждённые решения и существующие UI-компоненты. Не навязывать новый стиль и не менять утверждённые решения без разрешения.
2. Для содержательного редизайна или нового интерфейса исследовать подходящие работающие референсы. Проверять ссылки, desktop/mobile и конкретные приёмы. Отделять наблюдения от догадок; отдельно выбирать донора структуры и визуального языка. Не копировать чужие тексты, бренд, изображения или цельный узнаваемый дизайн.
3. **Единственный источник истины** для утверждённого UI — проектный `DESIGN.md` или его существующий эквивалент. Не создавать параллельный конфликтующий документ. Фиксировать роли типографики, палитру, сетку, breakpoints, отступы, состояния, доступность и обоснованные исключения. Черновые измерения референса держать отдельно от утверждённых значений.
4. Сначала переиспользовать существующие компоненты. Новую внешнюю библиотеку добавлять только после проверки лицензии, поддержки, зависимостей, доступности, адаптивности и влияния на загрузку. Каталог компонентов не является разрешением на копирование.
5. При необходимости использовать **один осмысленный выразительный приём**, не обязательный для каждого экрана. Пользовательское действие, читабельность и стабильность важнее эффекта. Нужны статический fallback, `prefers-reduced-motion`, поддержка браузеров и остановка анимации вне видимости.
6. Спорные решения сравнивать визуально, обычно 3–5 различимых вариантов. Интерактивный селектор только по запросу, без обязательной зависимости продукта от `?select`. Не публиковать режим выбора без отдельной авторизации; сохранять остальные URL-параметры и индексируемый canonical, исключать селекторные URL из sitemap.
7. Закреплять принятые решения в общих токенах/компонентах. Spec-тесты проверяют **конкретные** ограничения кода (запрещённые размеры, шрифты, обход токенов), но не заменяют проверку пикселей в браузере.
8. Для изменённых экранов проверять настоящие desktop/mobile и нужные промежуточные viewport, взаимодействия, переполнения, контраст, фокус, клавиатуру/тач, загрузку и `prefers-reduced-motion`. Для SEO-страниц проверять риск ухудшения LCP/INP/CLS, canonical и доступность основного контента без необязательных эффектов. Не объявлять Core Web Vitals PASS без измерений.
9. Отчёт должен различать **PROPOSED**, **APPROVED**, **IMPLEMENTED**, **VERIFIED**, **NOT RUN/BLOCKED**. Скриншот, spec-тест, lighthouse-замер и пользовательское утверждение — разные виды доказательств; отсутствие любого из них нельзя восполнять словами агента.
10. При конфликте приоритет имеют проектные `AGENTS.md`, утверждённые требования, оригинальные владельцы runtime и project-native gates; WFA не авторизует публикацию, миграцию, замену локальных Skills или нарушение ограничений Ludory.

**Выбор процесса:** [Interface Design](../playbooks/interface-design.md). Для отдельной критики использовать [visual-audit](../skills/design/visual-audit/SKILL.md), для доказательств реального рендера — [visual-qa](../skills/design/visual-qa/SKILL.md).

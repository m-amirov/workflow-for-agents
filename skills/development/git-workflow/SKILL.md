# Git Workflow: main-first

## Политика

**Начальная и конечная ветка агента — `main`.** По умолчанию работать непосредственно в `main`, если права, правила проекта и branch protection допускают это. Не создавать побочные ветки просто по привычке.

Если PR, изолированный worktree, параллельная работа или платформа требуют отдельную ветку, она **временная**. После реального прохождения обязательных проверок агент должен перенести все изменения задачи в `main`, вернуться в `main` и удалить только свои полностью интегрированные временные ветки локально и удалённо.

Это не разрешение обходить reviews, CI, branch protection или сохранять незавершённую задачу как успешную. Постоянное правило закреплено также в `AGENTS.md` и `rules/development.md`.

## До изменения

1. Проверить `git status --short --branch`, `git branch -vv`, `git worktree list`, `git fetch --prune origin`; определить актуальный `origin/main`, права и обязательные gates.
2. Не трогать незакоммиченные чужие изменения или worktree другого агента.
3. Если безопасно, перейти в `main` (`git switch main`), затем синхронизироваться без потери чужих коммитов (`git pull --ff-only origin main`); если ветка разошлась, разобраться с конфликтом вместо force/reset.
4. Если изоляция обязательна, создать временную ветку и сохранить её имя, начальный SHA, ссылку на PR и принадлежность этой задаче.

## Реализация

- Работать с минимальным диффом и коммитами, проверять состояние перед push.
- Прямой push только в разрешённую `main`, при выполнении требуемых gates.
- Если другая работа сдвинула `origin/main`, сначала безопасно синхронизировать.
- Не применять `git push --force`, `git reset --hard` или обход защиты ради завершения.

## Обязательное завершение

1. Проверить, что результат закоммичен и требуемые тесты/CI/reviews прошли на актуальном HEAD; не приравнивать старый PASS к текущему.
2. Если изменения в `main`, проверить, что они присутствуют в `origin/main` и зафиксировать SHA.
3. Если изменения во временной ветке, выполнить merge через PR при требовании review/branch protection; иначе разрешённым способом интегрировать их в `main`.
4. Проверить наличие всех нужных изменений в `main`. Для обычного merge можно применить `git merge-base --is-ancestor <branch-sha> origin/main`. Для squash/rebase проверить статус merged PR и эквивалентность итогового diff/контракта: старый SHA может не быть предком.
5. До очистки ещё раз проверить имя и принадлежность ветки, отсутствие нужных уникальных коммитов, незакоммиченных изменений и использование её другими worktree.
6. Вернуться в `main` в том рабочем окружении, где это допустимо.
7. Удалить собственную локальную ветку безопасно через `git branch -d <task-branch>` только если подтверждается ancestry. При squash, если `-d` отказывает, **не заменять автоматически на `-D`**: оставить ветку и сообщить о необходимости отдельной подтверждённой очистки.
8. Удалить собственную ветку на origin через `git push origin --delete <task-branch>` только после доказанного merge и повторной проверки её идентификатора. Сверить результат (`git fetch --prune origin`).
9. Отчитаться: `main SHA`, статус переноса, проверки, какие свои временные ветки удалены, какие остались и почему.

## Stop conditions

- Защищённая `main`, неуспешный CI/review, конфликты, отсутствие прав → `BLOCKED`, сохранить ветку и PR, сообщить причину.
- Ветка содержит неинтегрированные коммиты или рабочие изменения → не удалять.
- Ветка чужая, общая, релизная либо занята чужим worktree → не удалять.
- Нельзя доказать интеграцию после squash/rebase → не удалять.
- Никогда не удалять `main`, не применять массовую очистку, `git branch -D`, force-push или force-worktree removal по умолчанию.

## Completion criteria

Задача завершена только когда изменения действительно находятся в `main` и проверки пройдены; все безопасно удаляемые временные ветки этой задачи очищены. При препятствии сообщить `BLOCKED`, без выдуманного PASS.

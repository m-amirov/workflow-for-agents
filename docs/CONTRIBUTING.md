# Как пополнять базу

## Перед изменением

1. Найти существующее место: правило, Skill, playbook, knowledge, prompt или профиль проекта.
2. Проверить фактическую повторяемость и область применения.
3. Не копировать большие части документации другого репозитория.
4. Проверить публичность источников и отсутствие секретов.

## Новый Skill

- Создать `skills/<category>/<name>/SKILL.md`.
- Добавить YAML frontmatter с `name` и информативным `description` (когда применять и когда не применять).
- Описать шаги, ограничения, ожидаемые артефакты, критерии завершения.
- При необходимости добавить `references/`, `scripts/`, `assets/`.
- Добавить позитивные и негативные сценарии в `evals/cases/`.
- Обновить каталог, указать implemented без заявлений о validated до реальной проверки.

Пример: [root-cause-debugging](../skills/development/root-cause-debugging/SKILL.md).

## Новое знание

Записывать исходную проблему, наблюдения, версию среды, доказательства, статус первопричины, исправление, фактические проверки, ограничение применимости, ссылки на PR/commit/test. Если сведения ещё не проверены, явно обозначить гипотезу.

Не копировать токены, чужие персональные сведения, полные приватные логи и доступы. Если артефакт приватный, хранить ссылку и публичное обезличенное резюме.

## PR checklist

- [ ] Область изменения ограничена соответствующим разделом.
- [ ] Нет противоречий AGENTS.md и rules/.
- [ ] В каталоге корректный статус.
- [ ] Все ссылки и пути проверены.
- [ ] Сообщены реально исполненные проверки; неисполненные названы.
- [ ] Для изменений логики Skill есть regression/eval coverage, если разумно.
- [ ] Нет секретов или неподтверждённых утверждений о PASS.

## Версии

Для значимых изменений описывать миграцию, несовместимости и последствия существующих установок. Удаление/переименование навыков не должно молча ломать проектные профили.
